## 二、规则层延迟（红线指标）

**测的是什么**：`HomeAgent.decide()` 的端到端墙上时间，**含设备执行与审计写入**。
不测 `root.plan()` 单独耗时，因为用户实际感受到的是 `decide` 的总时间。

**方法**：25 条输入 × 60 轮 = 1500 次调用，每轮开始前先整体预热一次
（首次调用会触发模块懒加载，混进来会把 p95 拉高）。按漏斗**实际命中的 source 分组**统计。

| 分组 | 样本 | avg | p50 | p95 | max |
|---|---|---|---|---|---|
| `source=rule`（漏斗命中） | 1320 | **8.46ms** | 8.56ms | **20.59ms** | 42.50ms |
| `source=fallback`（非指令文本） | 180 | 0.46ms | 0.41ms | 0.57ms | 2.15ms |

> **为什么要分组**：输入集里故意放了两条漏斗打不住的（"氛围弄温馨一点"、"今天天气怎么样"），
> 它们会走到慢环。把这两条和规则命中的混在一起取平均，得到的既不是"规则层延迟"
> 也不是"端到端延迟"，而是一个**没有对应实体的数字**。这是本项目在多个地方反复
> 避免的一类错误（另一个例子是 `docs/架构图.md` 图 8 的内环告警 vs 感知层）。

**最慢的输入**（全部是场景联动，动作条数多）：

| 输入 | avg | 触发动作数 |
|---|---|---|
| 「睡觉了」 | 24.07ms | 4 条（关主灯 / 夜灯微光 / 空调自动 / 关窗帘） |
| 「我出门了」 | 16.77ms | 4 条 |
| 「我走了」 | 16.48ms | 4 条 |
| 「省电模式」 | 13.84ms | 3 条 |

**最快的输入**：「今天天气怎么样」0.40ms、「你好呀」0.41ms（走 ① 兜底，零设备动作）。

**结论**：延迟主要由**动作条数**决定（每条动作含一次 `registry.control` + 回读 + 审计
写入）。最慢一条 24ms 仍远低于 100ms 红线，因此规则层延迟**不是当前瓶颈**，
不需要为它做优化。

## 三、设备控制成功率

**方法**：对全部 64 个设备类工具，按其自身契约构造一次最小合法参数并调用。

| 分类 | 数量 | 说明 |
|---|---|---|
| 已执行成功（`ok=true`） | 60 | |
| 高危挂起待确认 | 4 | **预期行为，不是失败** |
| 真失败 | **0** | |

挂起的 4 项（均在 `lease.py` 的 `HIGH_RISK` 集合内）：

```
lock_entry_01__unlock              解锁门锁
lock_entry_01__set_lock_mode       切换门锁模式
camera_living_01__start_stream     开启摄像头直播
gas_stove_kitchen_01__turn_on      打开燃气灶
```

> **口径必须说清楚。** 若按 `ok / 全部工具` 算，成功率是 **93.75%** —— 这个数字
> 既冤枉系统（那 4 项是安全机制主动拦下的）又掩盖真相（掩盖了哪些动作被拦）。
> 因此本文件给两个口径：
> - **非高危动作成功率 = 60/60 = 100%**
> - **全量口径成功率 = 64/64 = 100%**（把"被安全机制正确挂起"计入成功）
>
> 对外声称"控制成功率 100%"时，**必须同时说明它的口径是"非被安全机制拦截的动作"**，
> 否则一旦有人拿一个未在 `HIGH_RISK` 里的高危动作做演示，这句话就当场作废。

## 四、慢环 LLM 延迟（未达标，如实报告）

**这一项没有在本次采集中重新测量**，原因是：慢环延迟由**服务商生成速度**主导，
随模型版本、时段、配额波动，单次测量不代表长期表现；把一次测量的结果写成"我们的
延迟是 X"是一种误导。

本节数据引自 `experiments/README.md` 实验五（2026-10-02 采集，模型 `glm-4-flash`），
那是一次**对照实验**而不是单点测量：

**固定输出、改变 prompt 体积**（33 倍差异）：

| prompt tokens | completion tokens | 耗时 |
|---|---|---|
| 51 | 17 | 3551ms |
| 567 | 16 | 2834ms |
| 1113 | 16 | 1311ms |
| 1659 | 17 | 1800ms |

→ prompt 扩大 33 倍，**耗时没有增加**（波动来自服务商侧，非 prompt 体积）。

**固定 prompt、改变输出长度**（15 倍差异）：

| prompt tokens | completion tokens | 耗时 |
|---|---|---|
| 51 | 13 | 1277ms |
| 51 | 48 | 2934ms |
| 51 | 87 | 6425ms |
| 51 | 196 | 11978ms |

→ 输出扩大 15 倍，**耗时线性增长**。

**结论**：`耗时 ≈ 1.2s 基线 + 输出 token 数 ÷ 15`。

**这个结论排除了三条看起来合理但实际无效的优化路线**：

| 曾被考虑的做法 | 为什么无效 |
|---|---|
| 重构管线减少调用次数 | 调用次数不是变量（实验已把 `1+N` 降到 `1`，墙上时间未改善） |
| 压缩 prompt 体积（元工具化） | prompt 体积不是变量（33 倍差异下耗时不变）。降级为**成本优化** |
| 让 Manager 批量翻译（`1+1` 次调用） | 模型无法可靠产出「多项 + 嵌套数组」响应，8 次探测全畸形，已回退 |

**唯一有效的两条**：减少输出 token（少提议几个动作），或换更快的模型 / 本地推理。

**因此本项目的对外口径是**：

- 规则层 P50 8.56ms —— 确定性、无外部依赖、覆盖标准场景集 100%（90/90）
- 慢环单次输出约 150–250 token，实测 8–13s；走**预算化降级，P95 有界**
- **不声称"慢环 P95 <5s"** —— 当前服务商下达不到这个目标

**现场重测命令**（需 API Key，约 2 分钟）：

```bash
python tests_performance.py --api
```

## 五、感知层与记忆层延迟

| 项 | avg | p95 | 样本 | 说明 |
|---|---|---|---|---|
| 感知层单次评估 | 0.088ms | 0.13ms | 300 | 4 模态 → 融合 → 门控 → 5 个情境参数 |
| 手册检索 | 0.027ms | 0.027ms | 300 | 8 条手册，纯关键词打分 |
| 经验检索 | 1.85ms | 1.98ms | 200 | 库内 200 条案例，逐行读 JSONL |
| 经验注入构造 | 1.89ms | 2.13ms | 200 | 含上面那次检索 |
| 习惯统计 | 0.79ms | 0.54ms | 50 | 含冲突检测（按设备分组） |

> **经验检索比其余项慢两个数量级，这是已知的、可接受的取舍。**
> `experience.retrieve()` 每次读取整个 JSONL 并解析（上限 2000 行）。
> 之所以不建索引：它只在**慢环**被调用一次，而慢环本身是秒级 —— 1.85ms 相对
> 8–13s 是噪声。用索引换这 1.8ms 会引入一份需要维护的派生数据，
> 收益与故障面不成比例。
> **但如果将来经验库涨到上万条，这个判断需要重做**（届时 `MAX_SCAN_LINES`
> 会截断，且 2ms 会变成 20ms+）。

**感知层 0.088ms 意味着什么**：当前感知层的模态检测器没有计算密集负载
（视觉是关键词模拟，面部/前庭是可选依赖）。**因此"国产算力加速"在本项目里
没有可加速的对象** —— `perception/gpu.py` 只是接缝，`status()` 返回
`has_hot_path=False` 并附警告。接入真实视觉推理前，不得把国产算力写成成果。

## 六、端到端演示链路延迟（估算，非实测）

把内环各环节相加，得到一次"环境异常 → 数字人告警 + 设备联动"的最坏情形延迟：

| 环节 | 延迟 | 来源 |
|---|---|---|
| 传感器 tick 间隔 | ≤ 2000ms | `config/loops.json` |
| 告警循环间隔 | ≤ 5000ms | 同上 |
| 阈值判定 | 0.015ms | 实测 |
| 事件路由（含 3 条设备动作） | ≈ 60ms | 按规则层单动作 20ms 估算 |
| WebSocket 广播 | < 5ms | 本机 |
| **合计** | **≤ 7.07s** | |

> **这是估算不是实测**：`alert_loop` 与 `sensor_loop` 的相位关系取决于启动时刻，
> 这里取的是两者间隔之和的最坏情形。写在这里是为了说明"为什么环境告警要等几秒
> 而不是立刻" —— 它由内环的两个固定周期决定，不是系统卡了。
> 若需要更快的响应，把 `config/loops.json` 的 `alert_seconds` 调小即可，
> 代价是 CPU 占用（每次判定 0.015ms，可忽略）。

## 八、这些数字不能用来声称什么

| 不能声称 | 原因 |
|---|---|
| "平均响应时间 8.46ms" | 那是**规则层**的数字。慢环是 8–13s，两者必须分开报 |
| "控制成功率 93.75%" | 那是把 4 个被安全机制正确挂起的动作算成了失败 |
| "控制成功率 100%" 而不加口径 | 一旦遇到未登记在 `HIGH_RISK` 里的高危动作就当场作废 |
| "慢环 P95 <5s" | 当前服务商下达不到（见 §四） |
| "感知层性能优越" | 0.088ms 是因为**当前没有计算负载**，不是因为算法快 |
| "并发能力 X QPS" | 本次采集全部是**单线程顺序调用**。并发极限另见 `tests_observability.py` 的线程安全测试，那是正确性验证不是性能测试 |
