> **灵犀 2.0：面向全屋异构智能家居的「确定性内核 + 可编排 LLM 外壳 + 门控式多模态感知」端云协同数字人中枢**

## 一、融合定位

灵犀 1.0 是一套骨架设计超前的智能家居 Demo：授权租约、单一真相源、能力注册表、
端云隐私分级、MCP 接入都已具备，但存在两类问题：

- **实现层**：17 处已确认缺陷，其中 4 处导致接口直接不可用（详见 `CLAUDE.md` 缺陷清单）。
- **能力层**：只有一个关键词模拟的"视觉检测"；LLM 只做一次 JSON 调用、无长期记忆；
  `capabilities.py` 与 `event_routes.py` 是未接线的孤岛；README 宣称的"可执行数字孪生"
  在运行时实际是死的（`twin_pairs` 恒为空）。

**感知能力、记忆能力与可靠性方法论，正是灵犀 1.0 最大的缺口。**

心镜（Xinjing AIGC Agent Platform）是一套已完成的心理健康多智能体平台。它的价值
不只是"另一套通用工程骨架"，而在于三项灵犀恰好缺失的技术资产：

1. **多模态置信度融合机制** —— 置信度熵 + 自适应加权 + 模态一致性复核（领域无关的真创新）
2. **白盒可解释参数体系** —— 用可解释的中间量替代黑盒端到端模型
3. **声明式判定范式** —— 把"信号 → 中间状态向量 → 离散类别"做成纯配置

因此本方案的融合定位是：

> **把心镜的「感知与可靠性方法论」装进灵犀的「护栏架构」里。**
>
> 不是拼接两个项目，而是让灵犀从「规则驱动的设备控制器」升级为
> 「**有感知、有记忆、可信赖、可证伪**的家庭 Agent」。

**改造落点**：直接改 `smart-home-controller` 主仓（`feature/xinjing-fusion` 分支）。
共 18 个提交、76 个文件、约 10,000 行新增。每个阶段收尾必须 12 个测试脚本全绿。

## 二、统一设计哲学（本方案最强的叙事）

> **同一个「不信任单一信号源」的原则，贯穿感知层与执行层。**

| 层 | 单一信号源的风险 | 门控机制 | 冲突时的行为 |
|---|---|---|---|
| **感知层** | 单模态误判（光照导致面部误判等） | 多模态置信度自适应加权 + 模态一致性欧氏距离复核（> 0.5 则丢弃） | 整组结果丢弃，标记 `requires_review` |
| **执行层** | LLM 幻觉 / 越权 / 重放 | 授权租约 + 状态版本校验 + 参数校验 + 高危二次确认 | 拒绝执行，写审计 |

两侧都是「**默认不信任、必须交叉验证、验证失败即拒绝**」。

**这不是巧合的类比 —— 两侧在代码里共用同一个 `Gate` 抽象**（`backend/gate.py`）：

```python
@dataclass
class GateResult:
    passed: bool
    confidence: float
    reason: str = ""
    evidence: dict = field(default_factory=dict)

class Gate(ABC):
    @abstractmethod
    def evaluate(self, subject) -> GateResult: ...
```

- `perception/modal_gate.py::MultiModalGate` —— 输入多模态读数，输出 `GateResult`
- `lease.py::LeaseGate` —— 输入待执行动作，输出 `GateResult`（**包装** `LeaseValidator`
  而非重写校验逻辑，避免两套校验分叉）

**收益**：两处门控的失败处理逻辑（记录 evidence → 降级 → 通知）因此统一；
且答辩时"感知层与执行层同构"这句话**有代码支撑而不是口头类比**。
`tests_perception.py` 第 6 节静态断言两个实现都满足 `Gate` 接口、都返回 `GateResult`。

## 四、逐项展开

### 4.1 多模态置信度融合

**算法三步**（忠实移植心镜已验证的机制）：

1. **单模态置信度**
   - 熵置信度：`c = 1 - H / log(N)` —— 概率分布越集中越可信
   - 稳定性置信度：`c = 1 - mean(σ) / MAX_STD`（`MAX_STD = 15.0`）
2. **自适应加权**：`w_i = c_i / Σc` —— 权重 ∝ 各模态自身置信度，而**不是固定权重**。
   一个模态自己都不确定时，它的话语权自动降低。
3. **一致性复核**：模态间**最大两两欧氏距离** > `0.5` → 判定冲突，整组丢弃。

**推广到 N 模态**是必要的改动：心镜只有两个模态，"两点距离"够用；四模态下
两两组合有 6 对，取最大者才能保证"任何一对冲突都算冲突"。

**与心镜的一处有意识偏离**：

> 心镜在"两者置信度都极低"时把置信度设为 `0.5` —— 等于从**零信息**里凭空造出一个
> 中等置信度的结果，然后照常参与决策。本项目改为**零信息即零置信度并拒绝**：
> `FusionOutcome(confidence=0.0, consistent=False, reason="所有模态置信度均接近 0，
> 无可用依据（不制造中间值）")`。

这不是为了不同而不同：0.5 这个数值会被下游当成"有一半把握"，而实际上
**没有任何依据**。在护栏架构里，把"不知道"伪装成"有点知道"是危险的。

### 4.2 白盒情境参数

| 参数 | 计算依据 | 真值来源（可验证） |
|---|---|---|
| 在家时长 | 人体红外连续触发累计 | 传感器时间戳（`PresenceTracker`） |
| 活动强度 | 各房间触发频次 + 设备操作频次 | 事件日志 |
| 作息偏离度 | 当日作息 vs 个人历史基线（±σ） | 历史统计 |
| 舒适度偏差 | 温湿度/空气质量 vs 设定舒适区 | 传感器 |
| 异常行为标志 | 深夜活动 / 长时间无活动 / 久卧 | 规则 + 时间窗 |

**每个参数都在前端可展开复核**：真值来源、计算方式、置信度、原始数据。
这是把"可解释性"从口号变成**可查证据**的地方，也是答辩时最该演示的面板。

**实施中发现并修掉的两个真问题**（由测试暴露，记录在此以免重蹈）：

1. `prolonged_inactive`（长时间无活动）原用「近期操作条数 ≤ 2」判定，把"环境不适"
   等场景也吞了。**操作少 ≠ 长时间没动** —— 改用 `idle_minutes`（距上次活动多久），
   后者才有时间维度含义。
2. `prolonged_inactive` 区域**永远不可达**：`anomaly` 规则排在它前面且条件重叠，
   同一现象被记两次。已按"具体 → 宽泛"重排区域，兜底规则置末。

### 4.3 记忆三源

| 源 | 内容 | 更新频率 | 落点 |
|---|---|---|---|
| 手册 | 设备说明书（静态知识，随仓库提交） | 几乎不变 | `memory/manuals.py` |
| 习惯 | 设备/场景使用统计 + 显式声明的偏好 | 每次操作 | `memory/habits.py` |
| 经验 | 成功规划案例（慢环 prompt 注入） | 每次慢环 | `memory/experience.py` |

**硬边界：记忆层只读世界，不写世界。** 三个源都不导入 `DeviceRegistry` / `lease`，
不产生任何设备动作。它们只能影响 **prompt**（进而影响 LLM 的提议），
而提议仍要过 Manager 的校验闸门。

这条承诺通过 **AST 去注释与 docstring 后的静态扫描**保证（`tests_memory.py` 第 4 节）——
理由与感知层相同：靠代码评审守不住，半年后有人加一句"自动应用学到的偏好"谁也不会注意。

**为什么扫描要先去掉 docstring 与注释**：模块文档里正大光明地写着"不导入 DeviceRegistry"
和"不该有 student_name 这种字段"。把说明当成违规，这条测试就变成"谁解释谁违规"。

### 4.4 快慢双环与可观测性

| 环 | 周期 | 是否调 LLM | 失效后果 |
|---|---|---|---|
| 内环 | 2–15s | **绝不** | 灯没开 → 用户立刻察觉 |
| 外环 | 每日一次 | LLM 优先 / 模板降级 | 日报没生成 → 用户第二天才注意 |

**这个差别的直接后果是：外环可以用大模型，内环不行。**

可观测性三件套是把上述说法变成**可复核事实**的基础设施：限流、API 统计、
模型调用日志与**决策分层延迟**。

> **为什么可观测性在本项目里是必需项而不是锦上添花**：模型调用失败会被上层吞成
> 「返回 None → 降级到规则层」，接口返回体上**看不出任何区别**。没有分层延迟与
> 降级率，"规则层亚毫秒 + 慢环预算化降级"这套说法就只是口头声称。
> `/api/metrics/llm` 返回真实决策样本的 `rule_path` / `slow_path` 各自的 avg 与 p95，
> **评委可当场调这个接口对**。

## 五、我们主动不主张的三件事

挑战杯是**学术科技作品竞赛**，不是商业赛。"引入一个信号 → 用交叉验证机制管住它 →
如实报告它的验证边界"这个完整链条，比"声称高准确率"更受认可。以下三项都是主动放弃
的主张，且都有实测或源码依据。

### 5.1 不主张"国产算力加速"

**心镜宣称的"MUSA → CUDA → numpy 三级自动探测链"实际只有两级** —— 读源码后确认，
不存在独立的 MUSA 代码路径，而是通过对 CUDA 设备名做 `metax` / `musa` 子串匹配来
识别厂商（`vibraimage/gpu_backend.py`）。

更重要的是：**灵犀感知层当前没有任何计算密集负载**（视觉是关键词模拟，
面部/前庭是可选依赖）。四模态融合 + 5 个情境参数一次评估仅 0.088ms（见 `docs/BENCH.md`）。

**没有可加速的对象，"加速比"就无从谈起。** 因此 `perception/gpu.py` 只作为接缝保留，
`status()` 返回 `has_hot_path=False` 并附警告"接入真实负载前不得作为成果主张"，
`tests_perception.py` 钉住这个断言。

> 写进 Future Work：接入真实视觉推理（帧差分/FFT/直方图）后，再给出 CPU vs 国产 GPU
> 的实测加速比。**在那之前不写任何数字。**

### 5.2 不做情绪测量

**心镜自己的评测报告证伪了它最亮眼的卖点**（VibraImage 前庭振动引擎，约 3000 行、
专著公式、10266 人常模）：

- 14 个参数修复后仅 **2/14** ANOVA 显著
- 稳定性 ICC 多为**负值**（aggression −0.47、charm −0.39）
- 用户的论文实验显示：微运动特征对效价 **r = 0.021**（≈ 无信号），
  而内容基线 r = 0.692

**因此本项目不做情绪测量，也不做任何准确率承诺。** 面部表情等信号标注为
**演示级**，如实报告验证边界。

**处理方式——「门控式融入」**：

1. 作为**第四感知模态**接入，而不是作为情绪判定器
2. 用**多模态一致性检验**管住它（冲突即丢弃）
3. 绝不进入控制回路
4. 文档里如实写出它的负面验证数据（本节）

> **值得指出的一点**：多模态一致性检验这个机制，**心镜自己的融合模块里已经有了，
> 但它没有用它来管住 VibraImage**。本项目把这两块接起来，是"同一套方法论在两个项目上
> 互相印证"，也与心镜 ESWA 论文"核心贡献是可靠性评估"的定位完全一致。

**答辩必答**：

> **"你们有心镜的心理健康背景，为什么不做情绪测量？"**
>
> 「本项目不做情绪测量。非接触式情绪识别在公开验证中 ICC 多为负值，我们不引入
> 未经充分验证的测量手段**作为控制回路的输入**。我们接入它，但用模态一致性检验
> 管住它，并如实报告它的边界。」

### 5.3 不声称"慢环 P95 <5s"

见 `docs/BENCH.md` §四。实测 `耗时 ≈ 1.2s 基线 + 输出 token ÷ 15`，单次 8–13s。
**服务商生成速度是唯一的硬约束**，当前配置下达不到 5s。

对外口径：**慢环走预算化降级、P95 有界**，不声称已达标。

## 六、被实测否决的路线（实证判断力）

原方案的核心改造点之一是**把慢环改为 prompt-based ReAct 工具循环** ——
这曾被列为"从心镜搬的核心创新点"，理由是心镜技术报告自己背书
「这套方案可复用到任何不支持 function calling 的大模型」。

**四条实验数据否定了它**（完整记录见 `experiments/README.md`）：

| # | 实验 | 结果 |
|---|---|---|
| 1 | ReAct 格式遵循度（15 个用例） | **80%（12/15）**，失败用例 3/3 稳定复现（模型丢 `<tool_call>` 标签改用裸函数调用语法） |
| 2 | 让 Root 直接输出具体 `{device_id, command, params}` 的幻觉率 | **0%（0/25）** —— 方案里"会引入幻觉"的风险假设**不成立** |
| 3 | 延迟归因（对照实验） | **与调用次数、prompt 体积无关**，只与输出 token 数线性相关 |
| 4 | 批量翻译可行性（8 次探测） | **全畸形** —— 模型无法可靠产出「多项 + 嵌套数组」响应 |

**因此最终实现 Design B**：Root **单次输出具体动作**，Manager **不再持有 LLM**，
成为纯护栏（校验 / 授权 / 执行 / 记录）。一次 `decide()` 的 LLM 调用数从 `1+N` 降到 `1`。

**另有一条值得记录的发现**：心镜的 ReAct 路径在其默认配置下**从未被跑到过** ——
`base_agent.think()` 用 `if self.platform == "lingshu"` 分流，而 `platform` 默认为
`None`；且 `stream_think` 在 lingshu 分支用 `tools=[]`，永远不吐 action/observation 事件。
**所以"心镜的 ReAct 有效"在此前没有任何实测依据。**

> **这一节写进申报书的价值**：它展示的是**用数据否决自己原方案的判断力**。
> 在科技作品竞赛里，这比堆机制更有说服力 —— 尤其是当被否决的那条路恰恰是
> "看起来更智能"的那条。

## 七、与心镜的差异化（不是照搬）

| 维度 | 心镜 | 灵犀 2.0（融合后） |
|---|---|---|
| 感知结果去向 | 直接进入分析链路与内容生成 | **只出询问式建议，绝不进入控制回路**（`PERCEPTION_CANNOT_ACTUATE = True`） |
| 融合模态数 | 2（固定 V-A 二维空间） | N（当前 4），一致性复核改为最大两两距离 |
| 零信息处理 | 回退到置信度 0.5 | **零信息即零置信度并拒绝** |
| 经验检索 | `random.sample` 随机抽样 → 自进化效果**无法验证** | **确定性排序** → 同样输入永远同样输出，可单测、可 A/B |
| 字段命名 | `student_name`（心理领域） | `context_key`（如"客厅\|light"） |
| 执行可靠性 | 无租约概念 | 授权租约 + 状态版本 + 高危二次确认 + 回读三态证据 |
| 感知层与执行层 | 两套独立机制 | **共用同一个 `Gate` 抽象** |
| 落库 | SQLAlchemy ORM（8 张表） | 内存 `StateStore` + JSON/JSONL（保住"pip install 即跑"卖点） |
| 中间件 | 无锁 `defaultdict`（并发下会错位） | 全部加锁，并有并发正确性测试 |

**明确丢弃的部分**：`database.py` 与 ORM 模型、`OrchestratorAgent`（它是硬编码串行
`for` 循环，不是 planner）、LangChain / LangGraph 层、AIGC 四个领域生成器、
SAS/SDS/SCL-90 量表、`tests/test_prompt.py`（已损坏，引用不存在的 `parsers/`）。

## 八、可复现性

融合工作的可复现性建立在三层上：

1. **门禁**：12 个测试脚本，全部离线可跑。
   ```bash
   export LINGXI_DATA_DIR=$(mktemp -d)     # 隔离运行时数据
   LLM_OFFLINE=1 python tests_smoke.py && LLM_OFFLINE=1 python tests_agents.py && \
   LLM_OFFLINE=1 python tests_capabilities.py && LLM_OFFLINE=1 python tests_edge_cloud.py && \
   LLM_OFFLINE=1 python tests_error.py && LLM_OFFLINE=1 python tests_funnel.py && \
   LLM_OFFLINE=1 python tests_budget.py && LLM_OFFLINE=1 python tests_perception.py && \
   LLM_OFFLINE=1 python tests_memory.py && LLM_OFFLINE=1 python tests_observability.py && \
   LLM_OFFLINE=1 python tests_loops.py && LLM_OFFLINE=1 python tests_performance.py
   ```
   > **`LLM_OFFLINE=1` 不是可选项**：否则测试会打真实网络请求，结果随模型输出波动而 flaky。
   > **`LINGXI_DATA_DIR` 也不该省**：否则测试会写进真实用户数据。

2. **基准采集**：`LLM_OFFLINE=1 python experiments/bench_collect.py` →
   产出 `experiments/bench_results.json`，`docs/BENCH.md` 的每个数字都来自它。

3. **方案选型记录**：`experiments/README.md` 记录了**被否决的路线及其数据**。
   改动架构决策前应先读它，避免重复已被证伪的路。
