# experiments/ — 方案选型的实测依据

这里存放**决定架构走向的实验**。每个实验都是为了回答一个"拍脑袋会拍错"的问题，
结果如实记录（包括不利结果）。申报书引用本目录的数字时，评委可按此文复现。

> 运行前提：`smart-home-controller/.env` 里配好模型 Key。实验会真实调用模型。

---

## 实验一：prompt-based ReAct 格式遵循度

**脚本**：`react_format_probe.py`
**运行**：`python experiments/react_format_probe.py 3`（每个用例重复 3 次）
**日期**：2026-10-02　**模型**：glm-4-flash

### 想回答什么

心镜项目把「prompt-based ReAct 工具调用」列为核心创新点，技术报告称
「可复用到任何不支持 function calling 的大模型」。但**该路径在心镜自身默认配置下
从未被走到**（`base_agent.think()` 按 `self.platform == "lingshu"` 分流，而该参数
默认 `None`），因此**没有任何实测依据**。本实验补上这个证据，以决定是否在本项目采用。

### 结果

```
格式正确率: 12/15 = 80%
延迟: 平均 2.8s  中位 2.2s  最大 6.2s
```

| 用例 | 结果 | 说明 |
|---|---|---|
| 单工具调用 | 3/3 ✓ | 标准 `<tool_call>` 标签格式，正确 |
| 需先查状态 | 3/3 ✓ | 正确请求 `query_home_state` |
| **多步链路** | **0/3 ✗** | **稳定复现的失败** |
| 应直接回答 | 3/3 ✓ | 不调工具，直接回答 |
| 应拒绝臆造 | 3/3 ✓ | 先 `list_devices` 确认设备是否存在，行为合理 |

**失败形态**（3 次完全一致，非随机）：

```
客厅空调当前温度是多少？需要调整到 24 度。query_home_state()
{"room": "客厅"}
```

模型**知道要调工具，但丢掉了 `<tool_call>` 标签**，改用裸函数调用语法。
可用更宽容的解析器（识别 `name(...)` + 后续 JSON）补救。

### 结论

1. ReAct 机制**可行**，但不是"开箱即用"——需要宽容解析器 + few-shot 加固。
2. 该失败用例（「把客厅空调调到 24 度」）在真实系统里**根本到不了慢环**
   （会被设备正则命中），所以实际慢环上的遵循度高于 80%。
3. **延迟上 ReAct 没有优势**：工具循环通常增加调用次数，而每次调用的耗时由
   输出 token 数决定（见实验二）。

→ **据此决定不采用完整 ReAct 循环**，改为单次结构化输出 + 强校验（Design B）。
理由与数据一并记入 `docs/融合技术白皮书.md`。

## 实验二：让模型直接输出具体动作 —— 幻觉率测量

**脚本**：`direct_action_probe.py`
**运行**：`python experiments/direct_action_probe.py`
**日期**：2026-10-02　**模型**：glm-4-flash

### 想回答什么

原方案否掉「Root 直接输出具体 `{device_id, command, params}`」的理由是
**"会引入幻觉"**，因此设计成两级翻译（Root 出高层目标 → Manager 翻成具体动作）。
但两级翻译要多花 N 次 LLM 调用。本实验量化幻觉率，看这个担忧是否成立。

### 结果

```
system prompt: 3161 字符（≈1975 token）
非对象返回: 0/5
动作总数: 25
幻觉动作（设备/命令不存在）: 0  → 0.0%
参数越界/非法: 0
单次调用延迟: 平均 10.3s  中位 8.0s  最大 17.7s
```

**幻觉率 0%。** 把完整设备清单 + 命令 + 参数范围给模型后，它严格照抄，不编造设备
或命令，参数也全部落在范围内。原方案的风险假设**不成立**。

### 结论

1. **安全前提成立**：Root 可以输出具体动作，且 Manager 的 `_verify` 是第二道防线
   （`tests_agents.py` 已覆盖"不存在的设备被 verify 丢弃"）。
2. **但延迟没有优势**：单次输出 token 变多（最多 8 个动作 → 17.7s），
   与两级翻译的总耗时相当。**管线重构不是降低延迟的杠杆。**
3. 采用它的理由是**架构更简单**：LLM 调用数 `1+N` → `1`，Manager 变成纯护栏
   （不再自己调 LLM），失败面更小。

## 实验三：批量翻译可行性（附带发现，无独立脚本）

在优化 Manager 的 `1+N` 次调用时，尝试过"一次调用翻译多个目标"。结果：

```
2 个目标：对象，但混入多余的顶层 actions 键
3 个目标：单元素数组 [{"results": [...], "actions": [...]}]
4 个目标：单元素数组
5 个目标：单元素数组
（各 2 次，共 8 次，全部畸形）
```

**glm-4-flash 无法可靠产出「多项、每项含嵌套数组」的响应。**

注意这与 `backend/llm_client.py` 的历史缺陷同源 —— 请求 `response_format:
json_object` 却收到数组，是该模型的**稳定行为**而非偶发。因此未在解析层做容错去
"救"它，而是**把不可靠的调用路径直接去掉**。

## 实验四：系统代理导致 LLM 层无声消失（附带发现）

| 路径 | 最小请求耗时 |
|---|---|
| 走 Windows 系统代理（`http://127.0.0.1:7897`，未启动） | **20–40ms 抛 `ProxyError`** |
| 直连 | 0.9–1.9s 正常 |

`chat_json` 的 `except` 把异常吞成「返回 None」，表现为 **LLM 层无声消失、
系统静默降级到规则层**，接口与界面都看不出异常。

智谱/DeepSeek/通义均为境内端点，本就不该走代理；且走代理时单次调用约 5–9s，
直连 1.4–3.3s，代理本身还在增加延迟。已改为默认直连（`resolve_proxies()`），
并补齐三处静默降级的告警。

## 实验五：延迟到底由什么决定 —— prompt 体积 vs 输出长度

**无独立脚本**（一次性测量，命令见本节末）
**日期**：2026-10-02　**模型**：glm-4-flash

### 想回答什么

方案原定做「工具元化」：把 system prompt 里 17 台设备的属性与命令全量列表，
换成 `list_devices()` 只回精简行 + `list_commands(id)` 按需拉，预计 prompt 从
约 3.2k token 压到 180 token。**这个优化到底能不能降低延迟？**

### 结果

固定小输出、逐步加大 prompt：

| prompt tokens | completion tokens | 耗时 |
|---|---|---|
| 51 | 17 | 3551ms |
| 567 | 16 | 2834ms |
| 1113 | 16 | 1311ms |
| 1659 | 17 | 1800ms |

**prompt 扩大 33 倍，耗时没有增加。**

固定小 prompt、逐步加大输出：

| prompt tokens | completion tokens | 耗时 |
|---|---|---|
| 51 | 13 | 1277ms |
| 51 | 48 | 2934ms |
| 51 | 87 | 6425ms |
| 51 | 196 | 11978ms |

**耗时随输出 token 数线性增长**，速率约 **14–16 tok/s**。

### 结论

1. **延迟 ≈ 1.2s 基线 + 输出 token 数 ÷ 15**。prompt 体积几乎不影响延迟。
2. **工具元化（prompt 瘦身）对延迟零收益**，只降低成本与提升可读性。
   该优化已从"延迟优化"降级为"成本优化"，不再作为阶段 1b 的验收项。
3. 唯一有效的延迟杠杆是**减少输出 token**（少提议几个动作）或**换更快的模型 /
   本地推理**。Root 的 prompt 因此加了「单次最多 4 条动作」的约束。
4. 这也解释了为什么管线重构（实验二、三）都不见效 —— 它们改变的是调用次数，
   而每次调用的输出量并没有减少。

复现命令：用 `requests` 直连 `backend.llm_client.resolve_proxies()` 指定的代理设置，
分别固定 `max_tokens` 与 system prompt 长度，读响应 `usage` 字段。

## 汇总：四条影响架构的结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | ReAct 可行但延迟无优势，不采用完整循环 | 实验一（80% 遵循度）+ 实验二（延迟相当） |
| 2 | Root 直接输出动作**幻觉率 0%**，原风险假设不成立 | 实验二（0/25） |
| 3 | 延迟由**输出 token 数**决定，与调用次数、prompt 体积无关 | 实验五（prompt ×33 → 耗时不变） |
| 4 | 模型端点必须**绕过系统代理**，否则 LLM 层无声消失 | 实验四（代理未启动时 20ms 失败） |

**因此不声称"慢环 P95 <5s"**。正确表述：
- 规则层 P50 7.4ms —— 确定性、无外部依赖、覆盖标准场景集 100%（90/90）
- 慢环单次输出约 150–250 token，实测 8–13s；走预算化降级，P95 有界
- 换更快模型或本地推理可线性改善（输出速率是唯一瓶颈）

### 对应到代码

| 结论 | 落地 |
|---|---|
| 1 | 不做 `react_loop.py`；写入 Future Work 并附本目录数据 |
| 2 | `RootAgent._llm_plan` 直接输出 `{device_id, command, params}`；`ManagerAgent` 不再持有 LLM |
| 3 | Root prompt 约束「单次最多 4 条动作」；元工具化降级为成本优化 |
| 4 | `LLMClient.resolve_proxies()` 默认直连 + 三处静默降级告警 |
